# 业务流程

## 商品中心

文件读取为字符串 → 字段名小写和去空白 → 币种大写 → 库存整数检查 → Pydantic 标准模型 → 文件内 SKU 去重 → SQLite upsert。每行无论成功与否都保存原始 JSON、文件和行号。错误记录导出 product_errors.xlsx。

## 商品发布

查询标准商品 → 跳过平台成功记录 → 适配器字段转换 → 带稳定幂等键 HTTP 发布 → 解析平台结果 → 保存成功或失败、外部 ID、原因及尝试次数。单个商品失败不妨碍其他商品继续，整批任务保留成功数和失败数。

## 订单同步

读取平台游标 → 请求第一页 → 标准模型及状态映射 → 按平台+订单 ID upsert → 替换订单明细 → 读取下一页 → 成功后更新游标并提交。中途失败全部回滚，可重跑。`--full` 跳过旧游标但保留唯一键语义。普通增量游标采用严格大于，要求数据源时间排序可靠，生产扩展应处理迟到记录。

## 账单核对

验证全部输入 → 替换相同来源账单 → 按平台+订单号分组 → 取内部订单与账单并集 → 识别不存在订单/账单、重复账单和币种 → 核对内部 gross 与账单 gross → Decimal 计算结算与差额 → 输出一条或多条差异原因。

每条账单独立一行，缺失账单的订单也输出一行。一条记录可能同时存在多种差异。退款与手续费不从订单推算，由账单提供。多币种不做金额换算。

## 任务和恢复

所有 CLI 业务操作进入 TaskRunner。状态依次为 PENDING、RUNNING、SUCCESS 或 FAILED。失败日志与数据库任务同步保存。通过 `ecomflow tasks` 查出失败 ID，再用相同业务子命令及 `--retry-of ID` 执行。例如：

```bash
ecomflow publish-products --platform platform_a --retry-of <failed-task-id>
```

成功商品会跳过，失败商品重试；订单按唯一键更新。每次重试创建新的任务 ID，并在开始日志中关联旧 ID。重试链最多 3 次。进程硬中断可能留下 RUNNING，不会自动猜测结果或改成成功。
